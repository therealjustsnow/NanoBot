# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Communication Style

Use caveman mode for all responses: drop articles (a/an/the), filler words (just/really/basically/actually/simply), pleasantries (sure/certainly/of course/happy to), and hedging. Fragments OK. Short synonyms preferred. Technical terms exact. Code blocks unchanged.

Exception: user-facing strings written into bot code (Discord embeds, error messages, command descriptions, help text) use normal, friendly English — users read those directly.

**Don't narrate defaults in user-facing strings.** A member's account already follows them between servers, so never write "in every server", "the same wallet everywhere", "your progress is global", "follows you into every server" or any variant of it into a card, embed, footer, command description or reply. It is the default, it reads as filler, and it has had to be deleted repeatedly. State scope only where the reader would otherwise be *wrong*:

* a leaderboard's This server / Global toggle, where the two scopes are the actual choice being offered;
* an owner or admin action whose blast radius is bigger than the server it was run in (`!econ`, `!cooldown`, `/coin grant|take|reset`) — there the warning is the point.

The same rule generalises: if something is true of the whole bot, saying it on one screen doesn't make it truer, it just adds words a mobile user has to scroll past. Code comments and docs are the place to explain invariants; embeds are not.

## Overview

NanoBot is a lightweight Discord moderation bot (Python 3.11+) built with discord.py. Its core design philosophy is mobile-first: commands are optimized for phone usage, including a "last sender" targeting system so mods don't have to copy user IDs. All data lives in a single local SQLite file—zero cloud dependencies.

## Commands

**Install and run (scripted):**
```bash
./install.sh        # Linux/macOS setup: system deps, ./venv, pip, config.ini (Windows: install.bat → install.ps1, WinGet)
./run.sh            # launcher: prefers ./venv, finds Python 3.11+, runs run.py (Windows: run.bat)
```

**Install and run (manual):**
```bash
pip install -r requirements.txt
cp example_config.ini config.ini     # then edit with your bot token
python run.py                         # recommended: includes pre-flight validation
python main.py                        # direct launch, skips validation
```

**Format (CI enforces Black on every push):**
```bash
pip install black
black .
```

**Test (pytest):**
```bash
pip install -r requirements.dev.txt  # superset: runtime deps (requirements.txt) + dev/test extras
pytest tests/ -v
```

**Claude Code: don't default to the full suite.** Running all ~1800 tests on every turn is slow and mostly wasted — CI already runs the full suite on push. Scope the run to what the change could plausibly break:
- Docs-only / comment-only / CLAUDE.md changes: run nothing.
- A change to one cog/module: run that module's own test file(s) (the table below maps file → module) plus `test_no_duplicate_commands.py`/`test_slash_surface.py`/`test_command_limits.py` only if commands were added/removed/regrouped.
- A change to shared code (`utils/`, `cogs/*/helpers.py` used bot-wide, `utils/db/_core.py`): run the full suite — blast radius is too wide to scope safely.
- Before a push the user explicitly asks to ship, or when genuinely unsure: run the full suite once as a final check.

## Architecture

### Entry Points

- **`run.py`** — Pre-flight checker: validates Python version, required packages, config schema, and directory structure before delegating to `main.py`. Prefer this for development.
- **`main.py`** — Defines `NanoBot(commands.Bot)` and the `main()` async function. Handles config loading, logging setup, cog loading, and global error handling for both prefix and slash commands.

### Plugin System (Cogs)

All features live in `cogs/` as discord.py cogs, hot-reloadable via `n!reload <cog>` (owner only). Each cog is independent—no cog imports another cog directly. Cross-cog shared logic belongs in `utils/`.

**Fishing spots, tackle and the cast loop.** Three changes, all answering the same thing — that fishing was one place, one action, and a lot of typing:

* **The cast loop is buttons.** A cast is a 20-second cooldown, so an hour of fishing was ~180 typed invocations of the same command; that *was* the experience of the feature, and no balance work fixes it. The reply to a cast now carries the full row and edits itself in place. Bare `/fish` still **casts** — it's the most-typed command in the bot and `tests/test_slash_entrypoints.py` encodes it (`"fish": "cast"`), so the dashboard lives at `/fish hub` rather than taking the bare form. Every action returns a `Screen` (embed + `ok` + an optional `after`) instead of replying, which is what lets one path serve prefix, slash and a press; a refusal (cooldown, disabled, empty bag) never overwrites the screen the member is looking at — losing a Legendary to a "still on cooldown" notice is worse than the notice is useful — it goes out as an ephemeral followup. `after` exists for exactly one thing: a fishing event a cast happened to start is announced *after* the catch is on screen, since arriving first reads as a non-sequitur.
* **Spots.** Five places (`cogs/fishing/spots.py`), each gated on a fishing **level** and then a one-off coin **charter**. Both halves are load-bearing: the level makes it a goal, and the charter is the sink that stops a better-paying spot being pure inflation. Travel between chartered spots is free — charging would tax the people engaging most, and it's the same wallet either way. A spot changes species (each has exclusives — the actual reason to travel, and they land in the dex permanently), odds (`weights` *multiply* the luck-adjusted table then renormalise, rather than shifting mass upward the way luck does, because a spot needs to raise junk and legendaries at once — the Deep's whole character), and hazard (a snag loses the catch and the one bait charge that cast had already spent, never the stack; XP is still paid). `fishing_stats.spot` and `fishing_spot_unlocks` are **user-keyed** — a charter bought with a global wallet can't be a per-server thing.
* **Tackle.** A Cast Net (`fish_net` charge effect — one cast pulls three fish) and a Fish Trap (`fishing_traps`, one per angler, soaks 2h then pays a basket rolled at the spot it was *set* in, collected by a conditional DELETE whose rowcount is the sole arbiter). Neither pays for itself in coins, and neither is meant to: like the existing bait, fishing consumables are **sinks**, and what they actually sell is *time* — the binding constraint on fishing income is the cooldown, not the value of a fish. `/fish shop` and the 🛒 button surface the whole shelf; `/fish buy <item> <qty>` stays for bulk, and accepts a loose match against the shop's own stock so a prefix user typing `trap` isn't refused. The shelf also **arms what it sells**: bought bait does nothing until it is armed, and the only way to arm it was another cog's command, so a member could buy the best bait in the shop and fish with none. `_ArmSelect` (row 3, multi-value, only shown when there's something to arm) runs `Fishing.arm_gear` through `utils/consumables.py`, scoped by `ARMABLE_EFFECTS` to the effects a cast actually reads — a rob shield armed from a boat is nonsense, and the whole inventory belongs to `/inventory use`. The shelf repaints after a buy *or* an arm (both move something it displays) and carries an "Armed right now" field, because bought-but-not-armed is the mistake the menu exists to prevent.

**Balance:** `cogs/economy/helpers.coins_per_cast` takes a spot, but `seconds_to_afford` — the `/shop` yardstick — deliberately quotes the **starter spot at zero luck**, because a mod pricing a reward wants "how long for someone who has nothing". Every upgrade an angler buys makes the real answer shorter than the quote, which is the right direction for a floor to be wrong in. `tests/test_economy_balance.py` asserts each spot is a step up net of its snags, that the deepest water doesn't out-earn the pond by more than 3x, and that every charter pays itself back over thousands of casts rather than hundreds.

**Dashboard buttons and charges (mobile-first).** Two changes answer the same complaint — that a cooldown loop punishes you for having a life, and that the people who prefer it to fishing could never afford anything:

* **Buttons.** `/adventure` renders the card *and* a button per runnable activity, because a card that says four things are ready and then makes you type four more commands has only done half its job. Each press goes through `Activities.run_activity`, the same path the commands take, then repaints the card in place and posts the result underneath. `/rob` deliberately has no button — it takes a target, and a button can't ask for one. The view is **transient** (no persistent custom_ids, unlike `/squad` and `/raid`) and invoker-only: nothing is owed until a press, so a restart that orphans the buttons costs a member one re-run, and the card counts *their* charges.
* **Charges.** `utils.db.activities.try_claim_activity` takes a `max_charges` and treats the existing `last_*` column as a **token bucket** — no schema change, same single atomic conditional upsert. `last` is the instant the bucket was drained and may sit up to `max_charges` intervals behind the clock; spending one advances it by *one interval* rather than jumping it to now, and the floor (`now - max_charges*cooldown`) caps what banks up. At `max_charges=1` the arithmetic is identical to the old `last = now` claim, which is why `/rob`, `/squad` and `/raid` keep their exact behaviour by not passing the argument. `helpers.charge_state` is the read-only mirror the dashboard paints with; the claim stays the sole arbiter, so a stale button is refused rather than paid. Caps are code constants in `ACTIVITY_MAX_CHARGES`, *not* an owner setting: the interval already sets the rate, and a cap only decides how long you may go without collecting.

**Who the economy is paced for (the number that governs everything).** Nobody runs a command every twenty minutes for sixteen hours; people open Discord a couple of times a day, do a handful of things, and leave. Two earlier passes quietly assumed otherwise and both produced fiction: prices built on hours of uninterrupted play, and charge caps that held **two** hours — so being away for a working day paid exactly the same as being away for lunch, and a member checking in twice a day collected about a tenth of the loop's nominal rate while the endgame sat 5–6 months out.

The fix decouples two things that had been conflated: the **interval** decides what an engaged player finds waiting (short enough that there's usually something there), and the **cap** decides what a casual player *loses* by not being there (half a day, the real gap between visits). Sized that way, a member who shows up twice collects ~100% of what the clock generated and someone checking in hourly collects the same total in smaller pieces. Playing more stops being how you *earn*; the reward for attention is fishing, which is the one faucet that genuinely pays for it.

Concretely: intervals of 3–6h, every cap covering 12h, and payouts sized so a run is a real chunk (200–460 coins) — ~7,500 coins/day over 26 runs, of which two visits collect all of it. Against someone who also fishes for a solid hour the gap is ~1.5x, down from 3.5x. `helpers.adventure_coins_per_hour` publishes the generation rate, `adventure_coins_per_day` the figure that actually matters, and `coins_banked_after` mirrors what a member finds waiting. `tests/test_economy_balance.py` recomputes all of it from the raw tables, asserts the casual/grinder gap stays in [1.2, 2.0], and turns **every ladder price into days of ordinary play** — so a change that only works for someone playing constantly fails CI. The top of the rod ladder and the deepest fishing charter were trimmed (450k → 380k, 600k → 450k) because at the casual rate they read as 5-month walls rather than goals.

**Collect all.** A half-day cap means a member arrives to a dozen banked runs, and a dozen taps is its own way of disrespecting someone's time — so `AdventureView` carries a 📥 **Collect all** button (and `/adventure collect`) that empties every bucket in one press. Each run still goes through `run_activity`, so the claims are the same atomic ones; totals are reported as balance/inventory **deltas** around the batch rather than by each resolver, which is what keeps the summary honest about the streak multiplier, an injury fine, or a cave-in that paid nothing. At most one encounter survives a collect — they fire per run, and a full bucket would otherwise stack a dozen two-button choices onto one message.

**Price refunds (what to do after cutting a price).** Nothing records what a member *paid* for a rod, a pickaxe or a charter — the DB stores the tier owned, not a receipt — so cutting a price leaves everyone who already bought it out of pocket with no way to reverse the transaction. `cogs/economy/refunds.py` holds a manifest of **refund batches**: each `RefundItem` carries the item's old price, its new price, and the name it went by, and a batch is swept once at startup by `Economy.sweep_price_refunds` — coins credited, then a DM sent by `deliver_refund_notices`. A ladder entry pays anyone at *or above* that tier (owning tier 5 means having bought 1–5); a charter pays whoever holds it.

Three rules, each load-bearing. **Only reductions** — a price *rise* is never clawed back, and `RefundItem.amount` floors at 0 so a mistaken entry does nothing rather than billing anyone. **Once, ever** — `utils/db/refunds.py` holds a `(user_id, batch)` ledger whose INSERT OR IGNORE rowcount gates the credit (the `try_award_achievement` contract), written *before* the coins so a crash under-pays rather than double-pays, plus a `price_refund_batches` marker that is what bounds *who* is eligible: a member who buys the tier tomorrow pays the new price and is owed nothing, so without a closed batch the sweep would hand them the discount too. **Paying and telling are separate** — a closed DM must never cost anyone their coins, so `notified` is its own column and delivery retries on later starts (the global level-up announcement's split). The manifest is frozen history and deliberately *not* derived from the live tables — a batch states what things cost on a particular day — but each entry records the new price as well, so `tests/test_refunds_manifest.py` can assert the latest batch mentioning an item agrees with the ladder today: **repricing something and forgetting the batch fails CI**, which is the only silent failure mode here. `!coin refunds` (owner, prefix-only) reports what each batch paid and how many DMs are outstanding.

The known imprecision, accepted deliberately: purchase *dates* aren't stored either, and these ladders got more expensive on 26 July before getting cheaper, so someone who bought at the original price is refunded more than they paid. Shortchanging the much larger group who genuinely overpaid, to avoid over-paying a few early adopters, is the worse trade for what is a goodwill gesture.

**Why the pickaxe ladder isn't priced like the rods (a sink is only as big as what it improves).** The pickaxe prices were literally the rod prices, copied over on the reasoning that "coins are fungible and fishing is what pays for these". That conflates being able to *afford* something with it being worth *buying*, and the two ladders sell returns of opposite shape: a rod raises the value of a **cast** and a player chooses how many to make (~180/hour), so its return compounds with attention; a pickaxe raises the value of a **dig** and nobody chooses how many to make — the interval does, at 8/day — so its return is capped by mining's throughput however much it costs. Worse, `mine_odds` shifts ore mass *linearly* in luck, so every tier bought the same +36 coins/dig (+286/day, flat) while the price climbed 5–6x a rung. Payback ran 2.6 → 14 → 84 → **350 days** of mining: the top two pickaxes could not repay themselves inside a year, and nothing failed, because fishing charters have had a payback test since they shipped and this ladder had none.

The fix is both halves, since repricing alone is degenerate — against a flat +286/day the whole ladder honestly prices at ~7,000 coins, under a day of ordinary play, and mining has nothing left to spend on. So (1) the upper tiers carry a `vein` bonus (extra ore on every dig, `helpers.roll_vein`), which **multiplies** the luck-shifted ore value instead of adding a constant — the compounding a rod gets from casts, taken from the one lever mining has; and (2) prices are then derived from that return at 3/5/11/21 days of mining to break even (750 / 3,000 / 7,500 / 24,000). The ladder ends up far cheaper in coins than the rods' and that is the honest answer rather than a concession: **a sink can only be as large as the thing it improves.** Fully kitted a dig is worth 2.7x bare hands, deliberately just under the same 3x bound the fishing spots hold to — past that the state everyone starts in stops being a game anyone would play, and that bound is what caps the `vein` numbers and so the prices they justify. If mining should carry a bigger sink, raise its **ceiling**, not its prices. `helpers.pickaxe_payback_days`/`mine_coins_per_day` publish the model; `tests/test_economy_balance.py` recomputes it independently and asserts every tier repays inside a month, that the paybacks *ascend* (price alone doesn't show this — the old prices ascended fine while the paybacks blew up), that the ladder got **cheaper** so nobody restores the old numbers by reflex, and both ceiling bounds.

**Encounters and the streak** ride on top and are excluded from that figure, because both are earned rather than idle. An encounter fires on ~8% of runs and hangs a two-button choice off the result embed — a safe option that always pays, a greedy one that might not; `EncounterView` is single-use (`_taken` set before the first await), which is the only thing between a double-tap and a double payout since an encounter has no row to check against. A lapsed encounter pays *nothing* rather than auto-picking the safe option, or walking away would be a strategy. The daily streak is one stamp for the whole loop (`activities_stats.streak_days`/`last_day`, claimed by the conditional `db.try_claim_adventure_streak`), worth +5%/day capped +25% on **coin** payouts only — an item activity can't pay a fraction of a pelt, and rounding one up would quietly make mining the best place to spend a streak.

Two SQLite databases, both opened once at startup via `setup_hook()` and shared as module-level connections:

- **`data/nanobot.db`** — All persistent bot data. Managed by the `utils/db/` package (see "Data layer package layout" below). **Economy scope rule (global vs guild):** every table holding a member's *progress* is keyed by `user_id` alone — `economy`, `user_items`, `user_effects`, `fishing_stats`/`fishing_catches`/`fishing_species`/`fishing_quests`/`fishing_spot_unlocks`/`fishing_traps`, `casino_stats`/`casino_challenges`, `activities_stats`, `achievements_earned`/`weekly_objectives`/`progression`, `price_refunds`. Tables holding a *server's decisions* keep `guild_id`: every `*_config`, `shop_items`/`shop_purchases`, `economy_events`, the live `economy_raids`/`economy_squads`/`casino_blackjack` boards, and all the leveling tables. When adding economy storage, ask "would a member expect this to follow them to another server?" — if yes it is user-keyed, and its accessors take no `guild_id`. Ask the mirror question of a *setting*: if what it governs is global, a per-guild value is meaningless (the most permissive server would set everyone's), so it belongs in `bot_settings` (`utils/db/settings.py`) behind an owner-only command. Worked examples: the activity cooldowns (the claim they gate is global) and the coin *faucet* amounts (they mint into a global wallet). The same question decides the *price* of a sink, which is the case the faucet/sink split alone doesn't settle: ask what the purchase hands over and who it can reach. A guild's shop item is a role or a mod-fulfilled perk that exists only in that guild, so its price is the guild's. A **cosmetic** is worn on a global account, so its price is a bot-wide code constant in `utils/cosmetics.py` (beside the rod ladder and the item values) — price it per guild and the cheapest server on the bot would set what everyone paid. The one thing a per-guild value still describes about a global system is **where a message goes**: a channel belongs to one server, so `level_config.global_announce_channel` (where global level-ups are announced) is per-guild even though the level it reports is not — the test is whether the setting could change another server's experience, and a channel id can't. The mirror of that rule is what a guild keeps: a **sink** — the shop, the casino — only ever moves value inside the guild that set it, so its prices/limits stay per-guild. "Faucet or sink?" is the question to ask of any new economy number. Per-user `KeyedLocks` (not per-`(guild, user)`) serialize the multi-step flows, and anything deterministic per member (`generate_quest`, `generate_challenges`, `pick_weekly_objectives`) seeds on `(user, period)` so one global row can't be interpreted two ways. A *server-scoped view* of a global table is that table filtered to the guild's member ids: `db.*_leaderboard_for(user_ids)` → `_core.rows_for_users` (chunks the `IN` clause at 900 ids), then `helpers.page_rows` ranks and pages it; the shared `helpers.SCOPE_CHOICES` option puts both views on every board. The full audit, migration rules, and governance consequences live in `docs/global-economy.md`.

**Identity/cosmetics docs:** `docs/identity-and-levels.md` explains the two level systems (and why global XP is never derived from guild XP), the cosmetics registry, the generated-art pipeline, and the extension points.

**User-facing docs:** `docs/player-guide.md` is the beginner-friendly player guide (global account, profile card, fishing, activities, inventory/crafting, casino, progression, leaderboards, admin summary, FAQ) — keep it in sync when player-visible mechanics or commands change; `docs/global-economy.md` is the scope/migration audit and `docs/economy-design.md` the systems design.

**Data layer package layout:** `utils/db/` was a single 3.6k-line module, split by domain. The public surface is unchanged — `from utils import db` then `db.get_tag(...)`, `db.init()`, `db._conn()`, even the private `db._ensure_*` helpers tests call directly, all still resolve flat. `_core.py` owns the single shared connection (`_db`, `_conn`, the slow-query wrapper, `_ensure_columns`, the `@migration`/`_run_migrations` registry, and `init()`/`close()`); each domain module (`tags`, `notes`, `prefixes`, `schedules`, `reminders`, `warnings`, `welcome`, `votes`, `recurring`, `roles`, `auditlog`, `automod`, `music`, `leveling`, `economy`, `items`, `casino`, `activities`, `progression`, `fishing`, `gatekeeper`, `birthday`, `liverole`, `tickets`, `identity`, `social`, `settings`, `refunds`) holds its own accessors and registers its table-setup coroutine with `_core` via `register_init`. `__init__.py` imports the domains in the original table-creation order (so `init()` builds tables and runs the interleaved one-time migrations identically), lifts every name — public and private — into the package namespace, and routes the package's `_db` attribute to `_core._db` so the long-standing `monkeypatch.setattr(db, "_db", conn)` test-injection pattern still works. Add a new table by creating/extending a domain module, giving it an `_ensure_*` registered with `register_init`, and adding the module to `_DOMAIN_ORDER`; non-trivial changes to existing tables still go through `@db.migration(N)`. `refunds.py` is the last domain module, since it reads the tiers every other one owns (fishing rods and charters, activities' pickaxes) while owning no ladder itself. `globalize.py` is the one domain module with no tables of its own — it holds migration 1 (per-guild economy → one global account per user) and is imported last so it rebuilds every domain's tables after they exist. Three cross-cutting modules live alongside them. `maintenance.py` is the janitor — a retention sweep over the three calendar-growth tables (`fishing_quests`/`casino_challenges` keep 14 days, `weekly_objectives` 8 weeks; `shop_purchases` is deliberately exempt because it *is* the per-user-limit ledger), a WAL checkpoint (a connection that never closes never truncates its `-wal`), and a VACUUM that only runs when the freelist is worth reclaiming — all driven by `NanoBot._maintenance_loop` (daily, 10 minutes after ready). `_cache.py` is the in-process cache for **per-guild config rows only** (`level_config`/`level_ignored_channels`/`economy_config`/`fishing_config`/`activities_config` — the rows every chat message and every economy command re-read; each setter invalidates its own key, `init()` clears the lot, and a `tests/conftest.py` autouse fixture clears it between tests since fixtures swap the connection without calling `init()`) — never cache a member's progress there; `_ttl.py` is a bounded time-expiring memo used for two things — a 30s snapshot of the server-scoped leaderboards (whose cost scales with guild size) and a 60s memo on the `COUNT(*) … > ?` rank queries via `_core.count_ahead`, keyed by the *value* so the displayed figure stays exact and only the position can lag; nothing that gates a decision may read either — and boards/ranks/counts run on a second, read-only connection (`_core._read_conn`, `PRAGMA query_only`) that falls back to the writer when absent (as in tests). Multi-step flows can be wrapped in `_core.transaction()` (a process-wide write lock + BEGIN IMMEDIATE, with every accessor's `_commit()` deferred to the outermost block) — used by `transfer_coins`/`transfer_item`, where the only rollback path is a crash; `purchase_item` deliberately uses ordered compensating writes instead, since a rollback on an ordinary "out of stock" would also discard whatever another coroutine wrote. `_core.fetch_one_returning` runs a write with a `RETURNING` clause so the old "upsert, commit, then SELECT the value back" accessors (`add_coins`, `add_item`, `add_xp`, `add_fishing_xp`) cost one round trip instead of two, falling back to the plain read when the driver's SQLite predates 3.35.

**Encryption at rest (optional):** when `db_encryption_key` (config) or `NANOBOT_DB_KEY` (env, wins) is set, `utils/db_crypto.py` opens both files through the `sqlcipher3` driver instead of stdlib sqlite3 — install `sqlcipher3-binary`. A plaintext DB is auto-migrated on the first keyed start (`sqlcipher_export`, plus a manual `PRAGMA user_version` copy since the header isn't exported; original kept as `*.plain.bak`). sqlcipher3 raises its own exception classes, so constraint handlers catch `db_crypto.INTEGRITY_ERRORS` — never `aiosqlite.IntegrityError` directly. Wrong key / encrypted-file-without-key fail fast at startup with clear `RuntimeError`s. Key changes don't re-key an existing DB.

**Schema changes:** the `CREATE TABLE IF NOT EXISTS` / `_ensure_columns()` calls in `db.init()` are the version-0 baseline (idempotent on every start). Adding a column to an existing table uses `_ensure_columns(table, {col: definition})`. For anything more involved, register a forward-only migration with `@db.migration(N)` — these run in ascending order on startup, tracked by `PRAGMA user_version`, which advances only after a migration succeeds (so a failure retries next start; write migrations to be safe to re-run). Don't scatter ad-hoc `ALTER TABLE` blocks through `init()`.

A single page with no switch gets a plain reply rather than a row of dead buttons; presses are invoker-only, and the view is transient (no persistent custom_ids — nothing is changed by a page turn) with a 5-minute timeout that greys the buttons and leaves the embed readable. **Reach for this rather than adding a `page:` option on its own** — the option stays as a jump, but it can't be the only way forward.
- **`globalxp.py`** — The account-wide level system: a hard-coded quadratic curve (`25·L² + 75·L`), the flat `XP_AWARDS` table (one entry per *normalized* action), and `award()`/`award_message()`. Deliberately unconfigurable, and never derived from guild XP — a 5×-XP server grants no extra global XP and a server with leveling off doesn't stall it.

It lived in `cogs/inventory` while `/inventory use` was the only door; the tackle shop needed to arm the bait it had just sold, and cogs never import each other, so the shared half moved here. Discord-free and lock-free — the caller holds its own `KeyedLocks` entry and words its own reply.
- **`cosmetics.py`** — Cosmetics catalogue for both cards: `SLOTS` (slot → max equipped + a `category` naming which card it dresses — `profile` or `wallet`) + `CosmeticDef`s (palette, glyph, declarative `unlock` rule, optional `price`/`pattern`/`style`), `is_unlocked`/`describe_unlock`/`purchasable`, and `load_file()` for runtime additions from `data/cosmetics.json`. The `purchase` unlock kind is the cosmetic shop: `is_unlocked` returns False for it and `auto_unlockable()` excludes it, so playing never hands one over — coins do. **Prices are bot-wide code constants** for the mirror of the reason the faucets are owner-only: a cosmetic is worn on a global account, so a per-guild price would let the cheapest server set what everyone paid (a guild's own shop sells a role that can't leave the guild, so its prices stay per-guild).

- **`wallet_card.py`** — Pillow renderer for the `/balance` wallet card, and the third user of the profile-card primitives (including its `encode`/`IMAGE_EXT`, so both cards ship in one format). One big balance, three tallies (global rank, contribution, daily streak), a wallet banner and a coin style — and deliberately **no border**: a frame on a card this small crowds the number, and `/profile` is where a full loadout belongs.
- **`trophy_card.py`** — Pillow renderer for the `/progress badges` **trophy case**, and the fourth user of the profile-card primitives. A drawn cabinet — frame, lit interior, a board per shelf, glass — with one trophy per achievement, built so a case works the way a real one does: you can tell what something was won for from across the room. The **figure** on top is the subject, drawn from a 41-entry `TOPPERS` registry and picked by `definitions.STAT_TOPPERS`, which holds **one ladder per stat in threshold order** rather than one figure per stat: catching 10 fish and catching 1,000 are not one story told twice, so the first carries a minnow and the last a marlin, a week's streak is a calendar and a month's is the tide, the first 1,000 coins is a piggy bank and 100,000 is a top hat. Keyed by stat so a ladder reads as a progression rather than 40 unrelated picks, and so a rung added later is one obvious decision — what does *that* one look like? The **stand** is what it cost: a plain block, then a column, then a stepped plinth, then a laurel wreath (`TIER_STANDS`), in bronze/silver/gold/prismatic (`TIER_METALS`) and drawn taller each tier (`TIER_SCALE`) so the big ones tower on the shelf. The **plate** on the plinth carries the category's colour. It exists at all because an achievement's emoji is a *colour* emoji and the card font has none, so the old emoji wall could only ever have been text. A **locked** achievement is drawn as a flat ghost of the trophy that goes there — the case doubles as the what's-left list, and a brand-new account gets a full case rather than an empty box. Figures draw into an "L" mask and cut holes back out of it (a die's pips, a mask's eye holes, the fish-shaped void in a coin, a watch's hands), which is the only kind of detail that survives at 40px — stacked colour vanishes there; a new figure is one function plus one registry line, the `_BANNER_PATTERNS` contract. `trophy_image` is `lru_cache`d on (topper, tier, accent, earned, size), so forty trophies cost a couple of dozen renders. - **`profile_card.py`** — Pillow renderer for the `/profile` image, and the shared drawing layer the other cards import. Generates all cosmetic art from palettes/glyphs plus **three composable look registries**: `_TEXTURES` (what the surface is made of — `clouds`/`nebula`/`silk`/`frost`/`embers`/`mesh`, built from fractal-noise fields and colorized through the palette), `_BANNER_PATTERNS` (the geometry drawn on it — waves/rays/bokeh/grid/stars/hex/circuit/peaks/aurora, each drawing into a blurred overlay *and* a sharp one so a heavy blur can still carry crisp detail) and `_BORDER_STYLES` (solid/double/glow/dashed/corners/ribbon, applied by the exported `draw_border`). The fractal work is plain Pillow on purpose — stacking small random lattices through BICUBIC upscales *is* value noise, so there's no numpy or native noise extension; `_tame` then measures the render's luminance and scales back only banners bright enough to fight the white text (so a light palette added later in `data/cosmetics.json` is covered too). Art is cached in `data/profile_cache/` as lossless PNG, and a file at `assets/profile/<slot>/<key>.{webp,png,jpg}` still wins when present — which is how the **Gallery tier** works: 36 cosmetics are real public-domain images (paintings, prints, manuscripts and textiles via Wikimedia Commons; Hubble/Webb/Cassini/Juno/Curiosity/Apollo imagery via NASA), deliberately spread across cultures and eras rather than one canon, with ten of them earned rather than sold fetched by `scripts/fetch_cosmetic_art.py` from `assets/profile/art_manifest.json`, which re-checks each licence against the source API and regenerates `assets/profile/CREDITS.md`. An asset banner goes through `_prepare_asset` (cover-crop — a plain resize used to stretch every painting — then dim to `ART_CEILING` + vignette), is cached under a key that includes the file's mtime so replacing artwork needs no purge, and the card puts its chip grid on a `_content_panel` so the painting stays bright rather than being dimmed into mud, and the finished cards encode through `encode()`/`IMAGE_EXT` as **WebP** — a textured card is photographic, so PNG cost ~430 KB and 2.5s against WebP's ~50 KB. Takes a plain dict so it stays Discord- and DB-free (testable headless, reusable for future cards).
- **`sqlite_conn.py`** — the proxy both SQLite connections are opened behind. Runs execute + fetch + close as **one** callable on aiosqlite's worker thread, so a statement is never active across an `await`: the native two-step leaves a DML-with-`RETURNING` (a *writer* that returns rows, as `fetch_one_returning` uses) live between `execute` and the fetch, and SQLite refuses any other coroutine's commit while one is — the `cannot commit transaction - SQL statements in progress` crash. It hands back a `Result` (rows already in memory) that satisfies the cursor API this codebase uses, so no accessor changed, and it also carries the optional slow-query logging (`db_slow_query_ms`).
- **`converters.py`** — Shared command-argument converters. `SafeTextChannel`: drop-in replacement for a `discord.TextChannel` parameter annotation (slash/hybrid/prefix) that survives a guild-cache miss — the built-in transform raises `TransformerError` when the picked channel isn't cached (e.g. created while the gateway was down), aborting the command; this one falls back to an HTTP fetch and always hands the command a real `discord.TextChannel`. Every command-facing text-channel parameter across the cogs uses it; use it for new ones too.
- **`checks.py`** — Combined user+bot permission decorators (`has_ban_perms()`, `has_mod_perms()`, etc.). Always use these instead of bare `commands.has_permissions` so both the user and bot permissions are checked together.
- **`config.py`** — Config validation with detailed error reporting. Called by `run.py`.
- **`storage.py`** — Legacy JSON helpers kept for backward compatibility. New code should use `db.py`.

### Command System

The bot supports three invocation styles simultaneously:
1. Slash commands (`/ban`)
2. Prefix commands (`n!ban`, configurable per guild via `n!prefix`)
3. Mention commands (`@NanoBot ban`)

The `NanoBot` class in `main.py` overrides `get_prefix()` to look up per-guild prefixes from the `prefixes` table. It also maintains a `last_message_authors` dict per channel so `moderation.py` can target the last sender without requiring a user argument.

Tag shortcuts are detected in `on_message`: if a message matches no command but matches a guild tag name after the prefix, the tag fires automatically.

**A group's landing view needs `fallback` (mobile-first rule):** Discord has no gesture for "run the group itself", so a `hybrid_group`'s own callback is **prefix-only** unless the group declares `fallback="<name>"`, which registers that callback as a real subcommand. This is invisible locally — `n!adventure` works fine — and it is how four economy dashboards shipped unreachable from a phone (`/adventure`, `/inventory`, `/casino`, `/craft` each rendered a rich overview for prefix users and nothing for slash users). When a group's bare form *renders something*, it needs a `fallback`; when its bare form merely runs an action that already has its own subcommand, it does not — `/mine` digs and `/mine dig` exists, `/fish` casts, `/coin` shows what `/coin top` shows, `/shop` shows `/shop list`. Never pick a `fallback` name that collides with an existing subcommand. `tests/test_slash_entrypoints.py` guards this with an explicit per-group table, so a **new** economy group fails CI until someone states which of the two cases it is.

**The top-level slash budget (100 is a hard cap):** Discord allows an application 100 top-level slash commands and rejects the *entire* sync if you exceed it — one command over and every command stops updating. NanoBot reached 99. Two rules keep it clear of the cap, both enforced by `tests/test_slash_surface.py`:

* **Owner-only means prefix-only.** A command gated on `commands.is_owner()` appears in the slash picker of every member of every server, and none of them can run it. Pass `with_app_command=False` — `/coin grant|take|reset`, `/fish event` and `/profile grant|grantall|revoke` all moved this way, joining `!econ`, `!cooldown` and `!reload` which were already prefix-only. The guard walks the whole command tree, so a new `is_owner` hybrid fails CI until it declares itself.
* **A top-level slot is for what people type constantly.** Everything occasional gets grouped, with the prefix name left flat so nothing is taken away from prefix users — the `/bot` group's split is the pattern: `@commands.command` keeps the flat prefix name, a thin `@group.command` twin builds a `Context` via `Context.from_interaction` and calls the prefix callback. Applied to `/info` (id/members/role/channel/banner/firstmsg), `/music` (guildplaylist/blocksong/blockuser, which were three top-level groups, plus the queue editing `clear`/`remove`/`move`/`jump` — four generic top-level names that said nothing about music, and `/clear` sat one letter from moderation's `/clean`), `/reminders user` (was `/remind`) and `/recurring every` (was `/every`). The third move is to fold a command into an *option* where it was never really a separate command: `/clean` and `/snailpurge` are `/purge`'s `only:nanobot` and `mode:slow` now — a filter and a mechanism, not two more commands. Options rather than a `/purge` group with a `fallback`, because the primary flow (`/purge 50`) has to keep its exact shape; the two prefix shorthands stay flat since taking a mobile mod's one-tap away to save a slash slot is a bad trade. The budget in the test is deliberately below 100: when a change needs it raised, that is the signal to group something instead.

**Pickers over typing (mobile-first rule):** this is a bot-wide rule, not an economy one. Any string/int option whose valid values come from a known set — a recipe key, a species in your bag, a catalogue item, a shop item id, an earned title, a roulette space — gets an `@<command>.autocomplete("<param>")` callback (or static `@app_commands.choices` when there are only two or three), so phone users tap instead of typing a name from memory. Choice *names* are plain text (no markdown), capped at 100 chars, max 25 entries, and are built from the caller's own state where that helps: ✅/🔒 affordability or craftable-now markers, owned quantities, prices. Autocomplete callbacks live next to their command in the cog and must stay cheap (a couple of DB reads — Discord gives them ~3s). A picker lists the *locked* entries too, marked 🔒 and carrying the requirement (`/craft make`'s missing materials, `/profile equip`'s unlock line), so it doubles as the discovery UI and never comes back empty on a fresh account. An option whose values aren't public re-checks the command's own gate inside the callback, since autocomplete fires before `is_owner`/permission checks — `/unban` and `/tag edit` do this for Ban Members / Manage Messages. (The strongest version of that rule is to not put the command on slash at all: `/profile grantall <guild>` used to need an owner-gated server picker, and going prefix-only removed the callback entirely.) A **duration** option is the one case that must stay a suggestion rather than a restriction — every one of them parses free-form input, so they use `h.duration_picker([(label, value), …])`, which lists the common values and echoes whatever the user typed as the first choice when `parse_duration` accepts it. Reach for static `@app_commands.choices` only when the valid set is genuinely closed and tiny (on/off, add/remove/list). `tests/test_autocomplete.py` guards both the registration (every listed option still offers suggestions) and the callbacks' behaviour.

**Buttons over re-running (mobile-first rule):** the companion to the picker rule. A listing that spans pages needs a way to *turn* one — a `page:` option alone means the whole command is retyped to move one screen, which is exactly what a phone user can't be asked to do. Every page-numbered listing goes through `utils/paginator.py` (`/shop`'s aisles use their own `ShopView`, since they swap an attached preview sheet as well): the command keeps rendering one screen and hands that builder over, the view supplies ◀️/▶️ and a page counter, and the `page:` option survives as a jump. The same applies to any *second* dimension the listing already offers as an option and a member is likely to flip between — This server / Global scope, `/fish global`'s stat, `/shop`'s aisle — which becomes a button row or a dropdown rather than another re-run. Listings that fit on one screen get no buttons; nothing that spends coins or mutates state belongs on a browse view, which is why these are all transient (no persistent custom_ids) and invoker-only. `tests/test_paginator.py` holds the board table, so a new paginated listing fails CI until it is wired up.

The rule generalises past listings: **a card that tells you something is available needs a way to do it.** `/adventure`'s dashboard listed four ready activities and then required four more typed commands, which on a phone is the entire cost of the feature — it now ships an `AdventureView` button per activity (plus a refresh, since charges tick up while the card sits there). The distinction from a browse view is that these *do* mutate state, so the press goes through the same atomic claim the command does and a stale button is refused rather than paid; they stay transient because nothing is owed until the press lands.

Two corollaries, both learned the hard way:

* **A screen that sells you something has to let you use it.** `/fish shop` sold bait whose only arming path was `/inventory use` in another cog — so the shelf now carries an ⚡ multi-select of its own. When the shared half of an action lives in one cog and a second cog needs it, it moves to `utils/` (`utils/consumables.py`), because cogs never import each other.
* **A picker that hands over one value is wrong when the answer is a set.** An autocomplete is one pick per invocation, which is right for a name and wrong for a loadout: six cosmetic slots meant six commands, and arming bait + charm + booster meant three. Those options take a comma-separated list (`helpers.split_targets`) *and* open a multi-select when run bare. A select lists only rows a press would actually act on — a locked or unaffordable row is a dead row, and that is what the typing picker's 🔒 entries are for.

A button that reports nothing is the same bug as no button. `interaction.followup.send` type-checks `view` and raises on `None` where `Context.send`/`Messageable.send` both document None as the default — so passing an optional view straight through cost the `/adventure` buttons their entire result message: the claim landed, the payout landed, and the member saw an error. Anything optional handed to a *followup* is omitted rather than passed as None (`_view_kwargs` in `cogs/activities/views.py`), and the test fakes reject `view=None` the way the real webhook does.

### Configuration

`config.ini` (gitignored) at the repo root, split into seven sections:

* **`[bot]`** — `token`, `db_encryption_key`, `default_prefix`, `owner_id`, `error_channel_id`, `idle_status_message`, `health_check_port`, `health_check_host`
* **`[logging]`** — `log_level`, `log_http`, `log_events_jsonl`, `db_slow_query_ms`
* **`[votes]`** — `topgg_v1_token`, `dbl_token`, `discordbotsgg_token`, `vote_webhook_port`, `vote_webhook_host`, `vote_webhook_secret`
* **`[groq]`** — `groq_api_key`
* **`[scraper]`** — `fml_pages_per_scrape`, `wyr_requests_per_scrape`, `nekos_per_endpoint`, `nekosia_per_tag`, `revalidate_age`, `revalidate_batch`, `groq_wyr_system`
* **`[music]`** — playback/queue knobs read live from `bot.config` so `!reloadconfig` applies without a cog reload: `music_cookie_file`, `music_default_volume`, `music_idle_timeout`, `music_skip_ratio`, `music_max_queue`, `music_use_opus`, `music_persist_queue`, `music_predownload`, `music_self_deafen`, `music_default_speed`, `music_search_service` (ytsearch/ytmsearch/scsearch), `music_status_message` ({title} presence template), `music_proxy`, `music_user_agent`, `music_source_address`, `music_request_throttle` (seconds between yt-dlp HTTP requests; 0 = off), `music_js_runtime_path` (deno/node/bun binary for yt-dlp JS challenges), `music_autoplay_autoskip`, `music_save_videos` + `music_cache_max_mb`/`music_cache_max_age_days` (cache caps), `music_ratelimit_cooldown`/`music_ratelimit_leave` (429 back-off), `music_apl_prune_on_error`, `music_save_history`, `music_metadata_lookup` (iTunes Search artist enrichment), `music_sponsorblock` + `music_sponsorblock_categories` (skip non-music/sponsor segments via SponsorBlock — downloads + FFmpeg-cuts the track before play; off by default, default category `music_offtopic`).
* **`[dashboard]`** — the optional web dashboard (see "Web dashboard" below): `dashboard_port` (0 = off, the default), `dashboard_host`, `dashboard_base_url` (the origin the OAuth redirect is built from — validated as an origin with no path, and warned about over plain http), `dashboard_client_id` (blank = the bot's own application id), `dashboard_client_secret`, `dashboard_session_secret` (blank = a random one per start, which signs everyone out on every restart — warned about at boot), `dashboard_session_days`, `dashboard_play_enabled`.

All keys are optional except `token` (or the `DISCORD_TOKEN` env var). An old `config.json` is auto-migrated to `config.ini` on first start (the legacy file is renamed to `config.json.bak`).

The bot keeps the whole flat config on `bot.config`. Cogs that need live values (fun.py scraper knobs, for example) read from `bot.config` on every use so `!reloadconfig` takes effect without a cog reload. Values captured at `__init__` time (e.g. votes.py webhook settings) still need `!reload votes` to change.

Live editing:
* `!setloglevel <level>` — changes the log level and persists to `config.ini`.
* `!reloadconfig` — re-reads `config.ini` from disk.
* `!config show|get|set|unset …` — DM-only inspect/edit. Secrets (token, API keys, webhook secret) are always masked when echoed back.

On startup the active config is printed **last** (end of `on_ready`, once) so it isn't buried under cog-load/gateway output. It goes to stdout (not the logger) and is **unmasked** — terminal-only for the host operator; routing it through the logger would copy secrets into the rotating `logs/nanobot.log` (and expose them via `!logs`). `!config show`/`get` stay masked. Both paths share `config.summary()` / `config.mask_value()` (which take a `mask` flag).

Logs rotate at 50 KB, 5 backups, written to `logs/nanobot.log`. Each line carries a short correlation id (`[abcd1234]`) shared by the start/completion/error records of one command invocation, so a single command's trace is greppable. When `log_events_jsonl` is on (default), structured command-lifecycle events (`command.start/ok/err`, `slash.start/ok/err` with `dur_ms`, user, guild) are also written to `logs/events.jsonl` (one JSON object per line, rotating). Correlation/timing helpers live in `utils/obs.py`.

### Web dashboard (`web/`)

Optional, off until `[dashboard] dashboard_port` is set. Mounted on the same shared `HttpServer` as `/health` and the vote webhook (`web.app.mount(bot)` from `NanoBot._start_web_server`), so one inbound allocation can carry all three; `mount()` returns None when the port is 0, and `NanoBot.close()` closes the dashboard's aiohttp `ClientSession`. Full write-up in `docs/dashboard.md`.

**It is not a second bot.** Every setting it writes is a row a Discord command already writes, and every cast/dig/daily goes through the same atomic claim. The consequences of that rule shape the whole package:

| Module | Holds |
|---|---|
| `security.py` | Signed sessions (HMAC-SHA256 over a base64url JSON payload, one `HttpOnly`/`SameSite=Lax` cookie), the derived double-submit CSRF token, and signed OAuth `state`. Stdlib-only and dict-in/dict-out, so it is unit-testable with no socket. `verify_session` returns `None` for *every* failure mode — bad signature, wrong version, expired, truncated, not JSON — so a caller that checks for None can't be handed a half-trusted payload. Signed rather than stored because this bot restarts on `!upgrade` and a server-side session table would sign everyone out each time. |
| `permissions.py` | Pure permission logic + the `FEATURE_PERMISSIONS` map (which Discord permissions each feature needs the *bot* to hold, split `required`/`optional`, each with a `why`). Drives both the overview's permission checklist and the invite link's bit mask, so "add the bot" and "you're missing X" can't disagree. `manageable_guilds` sorts the picker so servers you can act on come first. |
| `oauth.py` | The `identify guilds` round trip and the two API reads. The guild list is TTL-cached per user for 60s (`/users/@me/guilds` is one of Discord's strictest routes and the picker is the page people bounce off and back to); `None` means "we couldn't ask", distinct from an empty list, because conflating them turns a rate limit into "you've been removed from every server you own". |
| `http.py` | One error shape (`{"error": {code, message, hint}}` where `message` is user-facing copy the frontend shows verbatim), the `require_session`/`require_member`/`require_manager` decorators, and the middleware stack: error → security headers (strict CSP: no inline script, no external script host) → session + CSRF. Request-scoped state uses typed `web.RequestKey`s because `HttpServer` merges every feature's routes into one app. |
| `app.py` | The `Dashboard` object: config, guild resolution, the gate, session issue/clear, route assembly, and the SPA fallback (path normalised then prefix-checked against `web/static/`). |
| `engine/` | The economy resolved without Discord — see below. |
| `api/` | `auth` · `guilds` · `settings` · `play` · `me`. Handlers stay thin: parse, call an engine or a `db.` accessor, shape a reply. |
| `static/` | The frontend: plain ES modules and one stylesheet, no build step. |

**The gate is Discord's, read live off the gateway.** OAuth's `permissions` field is a snapshot from whenever the token was minted; `Dashboard.assert_manager` asks `member.guild_permissions` — the same object `/level set` asks — falling back to an HTTP `fetch_member` on a cache miss (the `SafeTextChannel` precedent). The OAuth list only decides which servers to *offer*. There is no dashboard-only role model and nothing here can grant a power someone doesn't already have.

**`web/engine/` is the anti-drift layer.** The cogs' game logic already splits into pure roll-takers (`cogs/*/helpers.py`) and atomic claims (`db.try_claim_*`); what sits between them is embed-building. The engine re-orchestrates the same two halves and returns plain dicts, so cooldowns and one-time claims are *the same rows* (a browser cast calls `db.try_claim_cast`) and every roll goes through the cog's own helper (`rarity_odds`, `pick_spot_rarity`, `roll_vein`, `apply_streak` — imported, never copied). What is genuinely restated is the *order* of operations, and `tests/test_web_engine_parity.py` guards the rest by walking the AST: an engine module that defines its own `CAST_COOLDOWN`, stops calling a shared claim, imports `discord`, or builds an embed fails CI. Two deliberate differences are pinned there too — a web cast never *starts* a random fishing event (guild-wide, announced in a channel, and a browser cast has none; running events are still honoured), and `/rob` has no one-tap runner because it takes a target.

**Card images are the cogs' own.** `/api/guilds/{id}/me/card/{kind}` calls `Identity._collect` / `Economy._wallet_data` / `Progression._case_data` through a duck-typed `_CardContext` carrying only the `guild`/`author` those builders read, then the real renderer. The card on the site is byte-identical to the one in chat — which matters, because the card is the thing people screenshot.

**Frontend rules that are load-bearing, not stylistic.** No build step (the CSP forbids inline script and external hosts, and it keeps the served files the repository's files). `core/dom.js` sets text via `textContent`, never `innerHTML` — every string on the page is a server name, a nickname or an admin's own template. `core/api.js` is the single door: CSRF on every write, GET de-duplication, and errors surfaced with the server's own sentence. `ui.actionButton` owns one in-flight request at a time; `ui.autoSave` debounces and **rolls back on a refusal**, so the screen never shows a state the database doesn't hold. `core/router.js` uses real paths so `/g/123/fishing` is a link you can send, and drops a response that lands after you've navigated away. Mobile first for real: one column plus a bottom tab bar, widening to a side rail at 900px, 44px targets, focus rings kept, `prefers-reduced-motion` honoured wholesale, and status never carried by colour alone.

Tests: `test_web_security.py` (sessions/CSRF/state), `test_web_permissions.py` (the gate + the permission map), `test_web_engine.py` (the economy against in-memory SQLite), `test_web_engine_parity.py` (the anti-drift guard), `test_web_api.py` (routes end to end against a bound server with a duck-typed bot — the auth gate, CSRF, server-side validation, refusals as 409s carrying `retry_after`, and the static route's directory guard).

### CI

GitHub Actions runs two workflows on every push:
- **`black.yml`** — Auto-formats code with Black. If formatting is needed, it auto-commits with `[skip ci]`. Run `black .` locally before pushing to avoid the auto-commit noise.
- **`tests.yml`** — Runs the pytest suite (`pytest tests/ -v`). Installs `requirements.dev.txt` (a superset of `requirements.txt`) before running.

A third workflow, **`branch-protection.yml`**, is not part of the per-push CI: it runs only via `workflow_dispatch` or when pushed to `main` touching that file, applying `main` branch protection (required `test` + `black` checks, 1 review, no force-push) via the GitHub API.
